# #2 Observability：回答に至る処理をたどる

目安 35 分。#1 で作った分析エージェント③を使い、**1 回の質問の裏側で何が起きているか**を調べます。

**この実習の到達点は、1 回の質問について「何がどの順で起き、どこで時間とトークンを使ったか」を自分の言葉で説明できることです。** 設定を変えて速さや費用を比べるのは #3 で行います。ここでは比べません。

**このエージェントには、実際の開発でよくある無駄が 1 つ、わざと入れてあります。** 手順 2 の質問では回答は正しく出て、エラーも出ないので、結果を見ただけでは気づけません。手順 3 で、Cloud Trace を使って探します。

### この実習で使うもの

| 名前 | 何をするものか | この実習での役割 |
|---|---|---|
| **教材の Web 画面** | Cloud Shell で起動し、「ウェブプレビュー」でブラウザから開く教材の画面 | 質問を送り、回答と根拠を見る |
| **Root Agent** | Web 画面の裏で動く AI。質問を受け取って #1 の③に分析を頼み、返ってきた表を確かめて回答をまとめる | 観測する対象 |
| **Cloud Trace** | 1 回の処理の中で、どの処理がどの順にどれだけ時間を使ったかを記録する Google Cloud の機能。1 つ 1 つの処理の記録を **Span** と呼ぶ | Root Agent の処理の流れを読む |
| **BigQuery のジョブ履歴** | BigQuery で実行されたクエリの記録 | 実際に実行された SQL を確かめる |

**流れ：** Web 画面で質問する → Root Agent が③に分析を頼み、回答をまとめる → Cloud Trace とジョブ履歴で裏側をたどる

Root Agent は、モデルに **Gemini 3.8 Flash** を使います。このモデルは地域を指定しない `global` で呼び出します（どの地域で処理するかを Google が選ぶ方式です）。教材のデータは架空ですが、自社のデータで使う場合は、処理する地域の要件を確認してください。

**なぜ #1 と違う画面を使うのか：** #1 では BigQuery Agents の会話画面から③に直接質問しました。業務でエージェントを使うときは、アプリ（ここでは Root Agent）がエージェントを呼び出し、回答を確かめてから返す形になります。会話画面では、この「呼び出す側」が何回分析を頼み、どこで時間を使ったかが見えません。そのため #2 では、Root Agent を動かす教材の Web 画面を使います。

## 開始前の準備

#1 を終えた状態（③まで作成済み）から始めます。#1 と同じ教材フォルダと Project を使います。**#1 で編集した Knowledge Catalog の定義は変えないでください。** 変えると、③とは別のエージェントが新しく作られます。

## 手順 1．#1 の質問の記録を、集計画面で確認する（5 分）

事前準備で開いた **BigQuery Agents の Monitoring** 画面を開きます（BigQuery → エージェント → Monitoring）。#1 で送った質問が、ここにまとめて集計されています。上から次を見ます。

1. **Overview**：Questions asked（質問数）と Conversations created（会話数）が 0 ではない
2. **Top agents**：「EC分析 ①〜③」が並び、それぞれの質問数が分かる（画面の幅によっては、表を右へスクロールすると見えます。会話数の列（Conversations）と取り違えないように注意します）
3. **Top knowledge sources**：①②が使った 5 つのテーブルと、③が使った `v_revenue_events`
4. **Estimated Usage** の Daily estimated token usage：1 日に使ったトークン数（推定値で、請求額ではありません）
5. **Performance** の Hourly answer latency：回答までにかかった時間（単位は秒。`50th` は中央値、`90th` は遅い側から 1 割の値）

この画面は 1 日・1 時間ごとの**集計**です。1 回の質問の中で、どの処理がどの順に動いたかは分かりません。それを手順 3 の Cloud Trace で確かめます。

**うまくいかないとき：** 反映には時間がかかることがあります。空の場合は、対象 Project と期間（右上の「直近 30 日」）を確認してください。

同じ記録は、ほかの画面からも見られます。

- **Metrics explorer**：Console のメニュー →「Monitoring」→「Metrics explorer」を開き、「指標の選択」の検索欄に `geminidataanalytics` と入力します。「Gemini Data Analytics Location」→「Chat」と進むと、入力・出力のトークン数（Input Token Count・Output Token Count）や、回答までの時間（Turn Latencies）などの指標が並びます。最近使っていないと出ない場合は、「Active」をオフにします。
- **Trace explorer**：Console の検索欄で「Trace explorer」を開き、フィルタに「OpenTelemetry サービス: `gemini-data-analytics-service`」を指定します。一覧の `google.cloud.geminidataanalytics.Chat` の Span ID を押すと、Data Agent の中のモデル呼び出し（`generate_content`）や SQL の実行をたどれます。一覧の「設定解除」は状態が未設定という意味で、失敗ではありません。

収集結果を保存する場合（日時は書式例で、自分の実行前の UTC 時刻へ置き換えます）：

```sh
cd ~/summit-workshop && uv run --locked python3 -m workshop.observability collect --since 2026-09-06T00:00:00Z
```

各 API の 1 ページを収集します。`nextPageToken` がある場合は全件収集ではありません。標準 Trace の親子 Span に同じ usage イベントがある場合は重複排除します。

## 手順 2．Web 画面で質問する（10 分）

Cloud Shell で、教材の Web 画面を起動します。

```sh
cd ~/summit-workshop && uv run --locked python3 -m workshop.web --port 8080
```

**確認：** `ブラウザの新しいタブで教材の画面が開きます` を含む行が表示され、入力が戻らなければ起動しています。このターミナルはそのままにしてください（閉じると画面も止まります）。`Address already in use` と表示された場合は、前に起動した画面が残っていることがあります。`pkill -f "workshop.web"` で止めてから、もう一度起動します。それでも同じ表示なら、`--port 8081` に変えて起動し、以下の 8080 を 8081 に読み替えます。

Cloud Shell のターミナルの上のバーにある「**ウェブプレビュー**」のアイコン（四角の中に目のマーク）→「**ポート 8080 でプレビュー**」を選ぶと、ブラウザの新しいタブで画面が開きます。「実行する」ボタンの下の「実行先」が、自分の Project ID と `ec_workshop` であることを確認します。

最初に入っている質問のまま「**実行する**」を押します。回答までに数十秒〜数分かかります。押し直す必要はありません。画面を再読み込みしても、サーバーが動いていれば分析は続きます。

回答が出たら、「回答」の欄で次を確認します。

1. **回答**
2. **Data Agent 呼び出し**の回数と**実行時間**。回数を控えておきます。なぜその回数になったのかは、手順 3 の Cloud Trace で確かめます。

**完了の目印：** 回答と Data Agent の呼び出し回数を確認したら、次へ進みます。

**うまくいかないとき：** 数分待っても結果が出ない場合は、ボタンを押し直さず画面を再読み込みします。失敗と表示された場合は、エラー文を控えて「うまくいかないとき・再開」を確認してください。

## 手順 3．処理をたどる（12 分）

Web 画面の回答の下にある「**Cloud Trace で処理を開く**」を押します。Cloud Trace の画面で、今回の 1 回の質問の処理が、時間の順に並んで表示されます。Trace の反映には少し時間がかかるので、表示されない場合は 1〜2 分待って再読み込みします。

左の列は処理の名前、右の青い棒はその処理にかかった時間です。上から順に読むと、どの処理がどの順で動いたかが分かります。名前の意味は次のとおりです。

| 画面の名前 | 意味 |
|---|---|
| `workshop.request` | 1 回の質問の全体 |
| `catalog.fetch_definition` | Knowledge Catalog から業務定義を取得する。数秒〜十数秒かかることがある |
| `invocation`・`invoke_agent ec_root` | Root Agent の処理全体 |
| `call_llm` | Root Agent の 1 歩分。モデルに次に何をするかを考えさせ、決めた道具を実行するまで。棒の長さには、道具を実行した時間も入る |
| `generate_content` | モデル（Gemini）への 1 回の依頼。トークン数はここで読む（`call_llm` にも同じ値が出るので、足さない） |
| `execute_tool analyze_ec` | 分析の道具。③に分析を頼む |
| `execute_tool compute_change` | 前月との差額を、AI ではなくプログラムで計算する道具（AI に引き算させると間違えることがあるため） |
| `execute_tool set_model_response` | 回答を作る |
| `evidence.two_consumers` | ③への分析の依頼をまとめた処理。この下に `data_agent.ask_data_agent` が並ぶ |
| `data_agent.ask_data_agent` | ③に分析を頼む |
| `evidence.review_table`・`evidence.calculate_change`・`evidence.validate_numeric_output` | 受け取った表の検査、差額の計算、最後に回答の数字の検査を、教材が行う |

次の 4 つを読み取ります。

1. **全体でどれだけかかったか**：画面上部の「期間」。
2. **どの処理が、どの順で動いたか**：左の名前を上から読みます。`catalog.fetch_definition`（業務定義の取得）→ `call_llm`（考える → `execute_tool analyze_ec` で③に分析を頼む）→ `call_llm`（考える → `execute_tool compute_change` で差額の計算）→ `call_llm`（考える → `execute_tool set_model_response` で回答の作成）→ `evidence.validate_numeric_output`（最後の検査）、のように進みます。モデルの判断で、`call_llm` の回数が変わることもあります。
3. **どこで時間を使ったか**：いちばん長い棒はどれですか。`call_llm` の棒には道具を実行した時間も入るので、モデル自体が考えた時間は、その下の `generate_content` の棒で見ます。`data_agent.ask_data_agent` は何本あり、合わせて何秒ですか。手順 2 の「Data Agent 呼び出し」の回数と比べます。
4. **トークンとエラー**：画面上部の、期間・スパンの横にある「生成 AI トークン数」（入力・出力）と、失敗を示す表示の Span がないか。

棒をクリックすると、その処理の詳しい情報（モデル名、トークン数など）が表示されます。

続いて、③が実際に実行した SQL を BigQuery で確かめます。

1. BigQuery の左のメニューで「**ジョブ履歴**」（画面によっては「ジョブエクスプローラー」）を選び、「**個人履歴**」タブを開きます。
2. 一覧は新しい順に並びます。上から、手順 2 の実行時刻（Web 画面の回答の下に表示された時刻）ごろのクエリを探します。作成日時の時刻が見えないときは、ジョブ ID を開いて詳細で確かめます。教材の検証では、手順 2 の直後なら、いちばん上の 2 件が③のクエリでした（③が 1 回の依頼の中で SQL を何本実行するかは、回によって変わります）。
3. ジョブ ID を押すと、右側に「ジョブの詳細のクエリ」が開きます。③のクエリを開いて、次の 3 つを見ます。
   - **SQL**：2 件以上あれば見比べます。
     - ③は同じ質問を 2 回頼まれ、そのつど SQL を書いています。書き方は回によって違うことがありますが、どちらも同じ質問に答えるための分析です。
   - **ラベル**：`data-agent-id` が `ec-poc-view-…`（③）になっているかを見ます。
     - なっていれば、③が実行したクエリです。`ca-bq-job: true` は、エージェントが実行したクエリの印です。
   - **処理されたバイト数と課金されるバイト数**：2 つの値を見比べます。
     - 教材の検証では、処理は数百バイトでも、課金は数十 MB でした。BigQuery は、参照するテーブル 1 つにつき最低 10 MB を課金するためです。③が見ている集計 View は、裏で 4 つのテーブルを読むので、1 回で約 40 MB になります。ただし、同じ SQL の結果がキャッシュから返されたときは、課金は 0 になります。費用は #3 で扱います。

**この「③への依頼が 2 本ある」ことが、冒頭で書いた、教材がわざと入れている無駄です。** Root Agent の中の「回答を作る処理」と「根拠を確かめる処理」が、同じ分析を③にそれぞれ頼んでいます。回答は正しく、エラーも出ないので、回答だけを見ても気づけません。Cloud Trace と BigQuery の記録を見て、初めて見つかります。実際の開発でもよく起きる無駄で、これを観測で見つけることが #2 の目的の 1 つです。教材の検証では、この 2 本がそれぞれ十数秒かかり、1 本ずつ順番に動いて全体の半分近く（4〜6 割）を占めていました。

#3 では、1 回目の結果を 2 つ目の処理にも使う「根拠を再利用」と、品質・時間・費用で比べます。

**完了の目印：** Cloud Trace で 4 つを読み取り、BigQuery のジョブ履歴で③が実行したクエリを開いて、SQL とラベルを確認できたら完了です。

**うまくいかないとき：** Trace が表示されない場合は、反映に時間がかかるため数分待って再読み込みします。それでも出ない場合は、対象 Project と時間範囲が合っているかを確認してください。開始時刻に「Undefined parameter - TIME_ZONE」と出るのは Console の表示の問題で、気にせず進めて構いません。

## 手順 4．質問を変えて、もう一度たどる（8 分）

手順 2・3 で読んだ処理の流れを、別の質問でたどり直します。次のどちらかを選びます（時間があれば両方）。自分で思いついた質問を試しても構いません。

- **A**：`2026年8月の純売上はいくらですか。`（前月との比較がない、単純な集計）
- **B**：`2026年9月に値引きを増やせば、必ず粗利益が増えると保証できますか。`（データでは答えられない質問）

実行する前に、手順 3 で見たことをもとに予想します。

- 手順 3 の 2 本の依頼は、質問の中身のせいでしょうか、エージェントの作りのせいでしょうか。作りのせいなら、別の質問でも 2 本になるはずです。この質問では何本になるでしょうか。
- 差額の計算（`compute_change`）は、前月との差を求める道具です。この質問は前月と比べていますか。比べない質問でも動くでしょうか。

質問欄に貼り付けて「**実行する**」を押し、回答が出たら「**Cloud Trace で処理を開く**」で予想と比べます。あわせて、全体の時間、モデルへの依頼（`call_llm`）の回数、画面上部の「生成 AI トークン数」も、手順 2 の質問と比べます。

最後に、次の 2 つを考えます。

- 観測で**分かったこと**と、**分からなかったこと**は何か（例：回答が業務として正しいかは、Trace だけでは分からない。B で答えを保留しても、Trace 上は正常に終わった処理に見え、エラーとは区別されない）。
- 本番でこのエージェントを運用するなら、問題が起きたときに原因を説明するには、何が見えていればよいか。

**完了の目印：** 予想と Cloud Trace の結果を比べて、当たった点か外れた点を 1 つ言えたら完了です。

任意 Challenge：`2026年8月に返金額が最も大きかった商品はどれですか。` を実行し、回答の金額が #1 の業務定義（返金は返金した日で計上する）に沿っているかを確かめます。7 月の注文を 8 月に返金した分も含めて、手計算で確かめてください。

## うまくいかないとき・再開

**Cloud Shell を開き直した場合**：教材フォルダに移動し、Web 画面を起動し直します。最後に実行した回答が「前回の回答」として表示され、Cloud Trace へのボタンからその処理の流れを開けます。

```sh
cd ~/summit-workshop && uv run --locked python3 -m workshop.web --port 8080
```

**ウェブプレビューが使えない場合**：Cloud Shell で直接実行できます。回答と、Cloud Trace を開く URL（`Traceを開く:` の行）が表示されるので、その URL から手順 3 に進みます。

```sh
cd ~/summit-workshop && uv run --locked python3 -m workshop.root_agent
```

別の質問で試す場合は、`--question "質問文"` を付けます。

## #3 への橋渡し

#2 で見つけた「③への依頼が 2 本ある」無駄は、#3 で「根拠を再利用」（依頼は 1 本）に変えて比べます。#3 ではさらに、分析担当の人が答える場合とも比べ、品質・時間・費用のトレードオフを見て、どの作りを選ぶかを考えます（実習 3 の教材は Summit に向けて後日公開予定）。#2 の実行記録はそのまま使わず、#3 で改めて質問を送ります。
