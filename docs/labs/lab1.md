# #1 Semantics：その「売上」、同じ意味で話していますか？

目安 35 分。架空の EC 企業で「売上は伸びたのに、なぜ利益が減ったか」を調べます。業務定義を伝える前後の回答と、集計 View を使った回答を比較し、数字の根拠を説明できるようになることが目標です。

進め方は 4 段階です。

1. 業務定義を伝える前の Agent に質問する
2. Knowledge Catalog で会社の業務定義を編集する
3. 業務定義を渡し、3 つの Agent を比較する
4. 意思決定につなげる（判断をまとめる）

### この実習で使うもの

| 名前 | 何をするものか | この実習での役割 |
|---|---|---|
| **BigQuery Agents** | BigQuery のデータについて日本語で質問すると、SQL でデータを調べて答えを返す AI | 同じデータを見る Agent を 3 つ用意し、同じ質問への答えを比べる |
| **Knowledge Catalog** | データや用語の説明を登録しておく、Google Cloud 上の「社内のルール集」。登録した 1 件を**エントリ**と呼ぶ | 「EC売上・粗利益の業務定義」というエントリに、売上や返金の計算ルールを書く |
| **教材のコマンド** | Cloud Shell で実行する、教材が用意したコマンド | エントリと Agent を作る。エントリに書いたルールを読み取り、Agent に渡す |

**流れ：** Knowledge Catalog にルールを書く → コマンドがルールを Agent に渡す → Agent に質問し、答えがどう変わるかを見る

Agent は、質問のたびに Knowledge Catalog を自分で読みにいくわけではありません。そのため、コマンドがルールを渡しています。**SQL を自分で書く必要はありません。**

データは 5 テーブル・合計 28 行なので、手計算でも答えを確かめられます。

## 開始前の準備

[共通の事前準備](preparation.md)が終わっていれば、そのまま手順 1 へ進みます。

## 手順 1．業務定義を伝える前の Agent に質問する（8 分）

同じ注文・返金データでも、返金をどの月の売上から引くかによって、月ごとの集計結果は変わります。この実習では、会社のルールを伝える前後で、AI の回答がどう変わるかを確かめます。

**始める前に、1 つだけ考えてみてください。** 7 月の注文を 8 月に返金したら、あなたならどちらの月の売上から引きますか。

注文の月から引く考え方も、返金した月から引く考え方も、どちらも筋が通ります。人によって分かれるこの判断を、定義を知らない Agent はどう扱うでしょうか。

**ここから操作です。** Cloud Shell で次のコマンドを実行し、質問する BigQuery Agents の Agent と、業務定義を書く Knowledge Catalog のエントリを準備します。**このコマンドでは、まだ質問は送信されません。**

```sh
cd ~/summit-workshop && uv run --locked python3 -m workshop.lab1 prepare
```

**確認：** `① 業務定義なし：エージェント カタログの「EC分析 ① 業務定義なし」` と、次の操作（1〜3）が表示されれば準備完了です。`prepare` の出力の `対象Project` が自分の Project ID であることも確認します。

`prepare` の出力の「1.」の行にある Knowledge Catalog の URL を開きます。ここでは**場所の確認だけ**を行い、編集は手順 2 で行います。**定義を知らない状態の回答を先に見るため**です。

1. 検索欄に `EC売上・粗利益の業務定義` と入力し、検索結果から同じ名前のエントリを開く。
2. **詳細**（Details）タブの**概要**（Overview）の横にある**編集**（鉛筆アイコン）を押す。業務定義の本文が行番号付きで表示される。
3. **12 行目と 13 行目の赤い文字**（`[[返金の計上日]]`、`[[返品で戻す原価]]`）を確認する。この 2 か所が、会社のルールがまだ書かれていない空欄で、手順 2 で埋める。
4. 何も変えずに**変更を破棄**を押して閉じる。

**このタブは開いたままにしておくと、手順 2 で戻るのが楽です。**

続いて、`prepare` の出力の「2.」の行にある BigQuery Agents の URL を開き、左のメニューで**エージェント カタログ**を選びます。「**EC分析 ① 業務定義なし**」のカードを押して開きます。

エージェントを初めて開くと「エージェントとのやり取りへのアクセスを許可する」が表示されることがあります。`prepare` が自分の Project に作ったエージェントなので、「**確認**」を押して進みます。

質問する前に、①に何が渡っているかを見ておきます。右側の「詳細」にある「**エージェントを編集**」を押すと、設定画面が開きます（エージェント カタログのカードの ⋮ →「編集」でも同じ画面です）。

- **ナレッジソース**：5 つのテーブル（見るデータ）
- **用語集（0）**：会社のルールは何も渡っていない

見終わったら、何も変えずに左上の **←** で戻ります。

> [!WARNING]
> 設定画面の「**保存**」「**公開**」は押さないでください。教材のコマンドは、エージェントが作ったときの設定のままかを確かめながら進みます。戻るときに変更を破棄するか聞かれたら、「破棄」を選びます。

送る質問は、次の 2 問です。`prepare` の出力の「2.」の行の下にも、`Q01:`・`Q04:` の後ろに同じ文が表示されています。下の枠の右上のボタンでコピーできます。

Q01

```text
2026年8月の純売上はいくらですか。
```

Q04

```text
2026年7月と比べて8月の粗利益が最も減ったカテゴリと、8月から7月を引いた差額を教えてください。
```

「EC分析 ① 業務定義なし」の画面に戻ったら（一覧に戻った場合は、もう一度カードを開きます）、画面下の「**質問する**」欄に Q01 を貼り付け、右端の送信ボタン（紙飛行機のアイコン）を押します。モードは表示されたまま（**高速モード**）で送ります。1 問に数十秒かかる場合があります。回答が返ってから Q04 を送ります。

各回答で、次の場所を見ます。

1. **数字と対象期間**：回答の中に出ます（1 行目とは限りません）。
2. **SQL**：回答の中の **⌄** を押すと表示されます（位置は回答によって変わります。②③の回答の冒頭にある「業務定義」の ⌄ は、ルールが開く別のものです）。記号が欠けて見える場合は「**エディタで開く**」で確認します（開くだけで、実行は不要です）。結果の表に `start_date` などの日付の列が出た場合は、質問した期間ではなく、データが実際にある最初と最後の日のことがあります。

Agent がどう考えたかを読みたい場合は、回答の上の「**思考プロセスを表示**」を開きます。

そのうえで、①の回答について次の 2 点を確認します。

1. **①はどう数えましたか。** 冒頭で考えた自分の答えと同じでしたか。例えば、次の場所に出ています（言い回しは回ごとに変わります）。
   - どの注文を数えたか：Q01 の回答の総売上の行（例：「キャンセルを除く」なら、出荷済み（SHIPPED）の注文も数えている）
   - 返金をどの月で引いたか：Q01 の SQL の `refunds` の `WHERE` の日付（`refunded_date` なら返金した月）
   - 返金や返品の原価をどう扱ったか：Q04 の回答の「指標定義」の行（教材の検証では、返金も回収した原価も入っていない回があった）
2. **それは誰が決めましたか。** ①には会社のルールを渡していません。正しい数字が出ていても、Agent が自分で選んだ結果です。

**①の答えは、実行ごとに変わることがあります。** 教材の検証で Q01 を送ったときは、①は 1 つの数字に決めず、「8 月の注文に対する返金を引くと 458,500 円、8 月に支払った返金を引くと 440,000 円」と 2 通りを並べました。返金を注文の月で引くか、返金した月で引くかの違いです。どちらも出荷済み（SHIPPED）の注文を売上に含めていました。

隣の人の①の答えとも比べてみてください。手順 3 では、ルールを渡した②③で、この判断が毎回そろうかを確かめます。

**完了の目印：** ①の Q01・Q04 の回答と SQL を見て、上の 2 点を確認できたら次へ進みます。

## 手順 2．Knowledge Catalog で会社の業務定義を編集する（7 分）

手順 1 で開いたエントリに戻ります。タブを閉じた場合は、`prepare` の出力の「1.」の行にある Knowledge Catalog の URL をもう一度開き、`EC売上・粗利益の業務定義` を検索して開きます。この URL から開けば、自分の Project で開きます。画面上部に出るのは Project の表示名なので、`対象Project` の ID とは違って見えることがあります。違う Project かもしれないと思ったら、画面上部の Project の名前を押し、一覧の ID の列で確かめます。

**概要**の横にある**編集**を押します。

この会社では、7 月の注文を 8 月に返金したら、8 月の純売上から返金額を引きます。また、返品された商品の原価を全部戻すのではなく、実際に回収できた原価だけを戻します。

次の 2 か所を置き換えて保存してください。

| 編集する文字 | 置き換える内容 |
|---|---|
| `[[返金の計上日]]` | `refunded_date（返金日）` |
| `[[返品で戻す原価]]` | `recovered_cost_jpy（実際に回収できた原価）` |

12・13 行目の 2 か所のほかは変更しません（1〜5 行目の `---` で囲まれた部分も変えません）。置き換えたら**保存**を押します。保存後の概要の表示に `[[` が残っていないことを確認してから次へ進んでください。

これは正解の数値を教える操作ではなく、会社が採用する業務定義を伝える操作です。その他の定義は最初から書いてあります。

保存したルールは、手順 3 でエージェントに渡します。

## 手順 3．業務定義を渡し、3 つの Agent を比較する（12 分）

手順 2 で書いたルールを、エージェントに渡します。エージェントは Knowledge Catalog を自分で読みにいかないため、Cloud Shell でルールを渡すコマンドを実行します。

```sh
cd ~/summit-workshop && uv run --locked python3 -m workshop.lab1 apply-rules
```

このコマンドは、エントリから手順 2 で保存したルールを読み取り、そのルールを渡したエージェント②と③を作ります。①はそのまま残します。

**確認：** 出力に `② 業務定義あり：エージェント カタログの「EC分析 ② 業務定義あり」` と `③ 業務定義あり＋集計View：…` の 2 行が表示されれば成功です。

**うまくいかないとき：** 「手順 2 の編集がまだ保存されていません」と表示された場合は、エントリの概要を保存したか、`[[...]]` が残っていないかを確認してから、もう一度このコマンドを実行します。

BigQuery Agents の**エージェント カタログ**に戻り、「**EC分析 ② 業務定義あり**」を開きます。同じ名前のエージェントが複数ある場合は、`apply-rules` の出力の `ID:` と同じものを開きます。まず「エージェントを編集」→「**用語集（1）**」→「用語を管理」の順に開きます。「カスタム条件」に「EC売上・粗利益の業務定義」があり、「定義」に手順 2 で書いたルールが入っていれば、ルールは渡っています。手順 1 と同じく、見るだけで、設定画面の「保存」「公開」は押しません。

| 設定の欄 | ① 業務定義なし | ② 業務定義あり | ③ 業務定義あり＋集計View |
|---|---|---|---|
| ナレッジソース（見るデータ） | 5 つのテーブル | 5 つのテーブル | 集計 View（`v_revenue_events`） |
| 手順（共通の指示） | 同じ | 同じ | 同じ |
| 用語集（会社のルール） | なし | 手順 2 のルール | 手順 2 のルール |

①②③をそれぞれ別のブラウザのタブで開いておくと、回答を見比べやすくなります。

②の会話画面に戻り、①と同じ Q01・Q04 を自分で送信し、回答・対象期間・生成 SQL を確認します。次に「**EC分析 ③ 業務定義あり＋集計View**」を開き、同じ 2 問を送ります。

Agent ごとに会話を分け、質問文は変えないでください。比較中に追加の条件を書き足すと、業務定義やデータモデル以外の差が混ざります。

①と②を比べると「ルールの有無」、②と③を比べると「見るデータの形」だけが違います。①の判断は実行ごとに変わるため、数字が 3 つとも同じになることもあります。その場合でも、次の 3 点の違いは見えます。

1. **回答の根拠**：②③の回答の「**業務定義**」（または「EC売上・粗利益の定義」）の ⌄ を押し、手順 2 で書いたルールが開くかを見ます。
   - ①はルールを知らないまま、自分で判断していました。
2. **SQL の注文の条件**：①と②の SQL で、どの注文を数えているか（`o.status` の条件）を見比べます。
   - ②はルールどおり**完了した注文だけ**に絞るはずです（教材の検証では `o.status = 'COMPLETED'`）。回答の文にも出ていることがあります（例：「COMPLETED注文の売上」）。完了した注文以外も数えていたら、ルールを渡しても判断を誤ることがある、という観察になります。
   - ①が `!= 'CANCELLED'`（キャンセル以外）のように絞っていたら、それは①が自分で決めた条件です。8 月には出荷済みでまだ完了していない注文（SHIPPED）が 1 件あり、①はこれも売上に数えています。
3. **SQL の参照元**：③の SQL の `FROM` を見ます。
   - 5 つのテーブルではなく**集計 View を参照**しているはずです（教材の検証では `FROM v_revenue_events` だけで、テーブルの JOIN なし）。回答の文にも出ていることがあります（例：「ビュー `v_revenue_events`」）。
   - この View は、販売を注文日、返金を返金日の出来事として 1 行ずつ並べ、完了した注文だけを、回収できた原価だけを戻す形で、あらかじめ組み立ててあります。②はルールを言葉で伝え、③は判断をデータの形に組み込んでいます。

**完了の目印：** ①②③すべてで Q01・Q04 を質問し、上の 3 点を比べられたら、振り返りへ進みます。

**答え合わせ：** 純売上は 420,000 円 − 65,000 円 − 115,000 円 ＝ **240,000 円**。Electronics の粗利益は 7 月 40,000 円、8 月 −24,000 円で、差額は **−64,000 円** です。この数字はエージェントには渡していません。①の答えがこれと違えば、①が自分で決めた数え方（出荷済みの注文を数える、返金を注文の月で引く など）が、会社のルールと違っていたということです。教材の検証では、①は純売上を 440,000 円や 458,500 円、Q04 を Apparel と答えました。

<details>
<summary>補足：OKF と、教材がルールを渡す仕組み</summary>

**OKF：** エントリの概要の 1〜5 行目（`---` で囲まれた部分）は、OKF という業務定義の書式です。種類・名前・説明を決まった形で書き、その下に本文を続けます。

**標準連携との違い：** エージェントが会話のたびに Knowledge Catalog を自動で検索する構成ではありません。教材のコマンドが Catalog のエントリから本文を取得し、エージェントの用語集（glossaryTerms）へ「カスタム条件」として書き込んでいます。用語を管理する画面で「Knowledge Catalog（0）からインポートされました」と表示されるのは、このためです。

**テーブルの列の説明：** 5 つのテーブルの列には、その列が何かだけを説明として付けています。計上のルールは書いていません。列の説明にルールを書けば、それもエージェントへの業務定義になります。

**検証済みクエリを使わない理由：** 設定画面の「検証済みクエリ」（質問と SQL のペア）は使っていません。正解の SQL を渡すと、ルールやデータの形の効果を比べられなくなるためです。決まった SQL で答える方法は、#3 の任意 Challenge で比べられます。

</details>

## 手順 4．意思決定につなげる（8 分）

採用する定義によって、Q04 の答えは Electronics（会社のルール、②③）にも Apparel（①）にもなりました。**もし①の答えを信じていたら、次にどのカテゴリを詳しく調べ、どのカテゴリを見落としていたでしょうか。**

そのうえで、次の 3 点を説明できれば基本課題は完了です。

1. 売上・返金・回収原価を、どの月に計上するか。
2. 回答を信頼するために、数字以外に何を確認したか。
3. 自社で定義を決める人、データモデルに反映する人、結果を検証する人は誰か。

<details>
<summary>答えの例</summary>

1. **計上する月（教材の会社のルール）**
   - 売上：注文した月。数えるのは完了した注文（COMPLETED）だけ。
   - 返金：返金した月（`refunded_date`）。
   - 回収原価：返金した月に、実際に回収できた原価（`recovered_cost_jpy`）だけを戻す。
2. **数字以外に確認したこと（例）**
   - 回答に業務定義が引用されているか。
   - 対象期間が質問どおりか。
   - どのデータを見て、SQL の条件が会社のルールどおりか。
     - ②：元のテーブルで、完了した注文だけ（`status = 'COMPLETED'`）を数え、返金を返金した日（`refunded_date`）で絞っているか。
     - ③：集計 View（`v_revenue_events`）だけを使い、期間を `event_date` で絞っているか。完了した注文の選別と、返金を返金した日に計上することは、View の中で済んでいます。
   - 28 行のデータで手計算した答えと合うか。
3. **担当する人（例。自社に合わせて考える）**
   - 定義を決める人：経理や事業部門。
   - データモデル（集計 View）に反映する人：データエンジニア。
   - 結果を検証する人：分析担当や、数字を使う業務部門。

   1 人が全部を兼ねると、定義の誤りに気づきにくくなります。

</details>

手元のメモに、採用する定義と根拠を 1 行残してください。自社の用語の下書きもメモに残します。

<details>
<summary>補足：この実習が SOAP アーキテクチャのどこにあたるか</summary>

Google Cloud は、データに意味を与えて AI エージェントの土台にする構成を **SOAP（Semantic and Ontology Agent Platform）** として説明しています（[公式ブログ](https://cloud.google.com/blog/ja/products/ai-machine-learning/soap-architecture-turning-data-stored-in-s3-into-a-foundation-for-ai-agents-on-google-cloud)）。3 つの層からなります。

| SOAP の層 | この教材での扱い |
|---|---|
| つなぐ層（Borderless Lakehouse、クロスクラウド接続） | **扱いません。** 教材データは BigQuery に置きます |
| 意味を与える層 | **#1 で扱う中心です**（下の表） |
| 働かせる層（エージェント実行） | #1 の BigQuery Agents、#2・#3 の Root Agent |

「意味を与える層」は 3 要素からなり、この教材の対象は次のとおりです。

| 要素 | 対応サービス | この教材 |
|---|---|---|
| 共通オントロジー | OKF ＋ Knowledge Catalog | **#1 の中心。参加者が編集します** |
| ナレッジグラフ | BigQuery Graph | **扱いません** |
| セマンティック層 | LookML / Looker | **扱いません** |

**この教材は SOAP の全体像を再現するものではありません。** 「意味を与える層」のうち共通オントロジーを手で動かし、その効果を回答の違いとして確かめることが #1 の範囲です。

また、**教材の実装は公式の構成そのままではありません。** Data Agent が会話のたびに Catalog を自動検索するのではなく、教材コードが Catalog から定義を明示的に取得して Agent へ渡しています。詳しくは手順 3 の補足を参照してください。

## 任意 Challenge：同じ質問をもう一度（10 分）

手順 1 で、「①の答えは実行ごとに変わることがある」と書きました。本当にそうか、自分で確かめます。

1. エージェント カタログで「EC分析 ① 業務定義なし」を開き、新しい会話を始めます（前の会話の続きにしないため）。
2. 手順 1 と同じ Q01 を、そのまま送ります。
3. 前の回答と比べます。数字、前提（返金をどの月から引いたか、出荷済みの注文を含めたか）、SQL、回答までの時間は同じでしたか。
4. 余裕があれば、②にも同じことをします。②の答えは、前と同じになりましたか。

**考えてみましょう**：同じ質問でも答えが変わることがある AI を、業務で使うには何が必要でしょうか。手順 4 の「回答を信頼するために、数字以外に何を確認したか」を思い出してください。

> 1 問ごとに、AI の利用料金が少しかかります。講師の案内する時間の範囲で進めてください。

## 再開・トラブル時

| 状況 | 対応 |
|---|---|
| ②③が作られない | Knowledge Catalog のエントリの概要を保存したか、`[[...]]` が残っていないか確認してから `apply-rules` を再実行 |
| Knowledge Catalog でエントリが見つからない | `対象Project` が同じか確認し、30 秒ほど待って `EC売上・粗利益の業務定義` を再検索。解消しなければ表示された `Knowledge Catalog Entry` を主催者へ共有 |
| エージェントがカタログに見つからない | Console の Project ID と `prepare` の出力の `対象Project` が同じか確認。名前ではなく ID（`ec-poc-…`）で表示されている場合や、同じ名前が複数ある場合は、`prepare`・`apply-rules` の出力の `ID:` と同じものを開く |
| Cloud Shell を閉じた | Cloud Shell を開き直し、止まった手順のコマンドをもう一度実行。`uv: command not found` なら[事前準備の手順 1](preparation.md#手順-1実習用の環境を用意する)の折りたたみを確認 |
| `You do not currently have an active account selected` と表示された | Cloud Shell を長く使わずにいると、認証が切れることがあります。Cloud Shell を閉じて開き直し、同じコマンドをもう一度実行 |
| 権限・API・課金のエラー | エラー文と対象 Project を主催者へ共有。トークンや鍵は共有しない |
| 質問の送信に失敗した | 同じ会話でエラー文を確認。原因を解決してから新しい会話で再送する |
| 以前の実習から再開した | 定義がすでに完成していれば、`prepare` の出力に①②③がすべて表示される。手順 2 の編集は省略し、現在の定義のまま比較を続ける |
| 定義を最初からやり直したい | 参加者の定義や回答を削除せず、初回状態からの確認には新しい Project を使う |

環境トラブルが解消しない場合は、教材の検証で記録した回答を使って比較・振り返りを続けられます。Cloud Shell で次を実行し、「ウェブプレビュー」でポート 8081 を開きます。

```sh
cd ~/summit-workshop && uv run --locked python3 -m workshop.lab1 serve --example --port 8081
```

自分の Project への接続や新しい推論ではなく、記録の再生です。

公式資料：[BigQuery Agents で会話を開始する](https://docs.cloud.google.com/bigquery/docs/create-conversations)、[Cloud Shell のウェブプレビュー](https://docs.cloud.google.com/shell/docs/using-web-preview)。
