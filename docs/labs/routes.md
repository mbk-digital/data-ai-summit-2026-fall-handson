# Challenge E2：3 つの処理経路を比較する

同じ EC 分析 Root を使い、「どの処理を Data Agent に任せるか」を比較します。目的は最安の構成をあらかじめ決めることではなく、品質・対応範囲・時間・全体の参考費用を見て採用条件を考えることです。結果は、#3 と同じく Cloud Shell で起動する教材の Web 画面で、URL の末尾に `/benchmarks` を付けて開きます。Runtime へのデプロイは不要です。

## 3 構成の違い

| 指定 | 挙動 | 対応範囲外・失敗時 |
|---|---|---|
| `data_agent` | Data Agent へ質問を渡し、Root が返ってきた集計結果を基に回答 | 取得失敗は失敗として残す |
| `verified_sql` | 対応する質問を固定の SQL テンプレートで BigQuery に問い合わせ、同じ Root が回答 | 対応範囲外は `UNSUPPORTED`。別経路へ自動転送しない |
| `router` | 質問文と対応する定義から、SQL か Data Agent をアプリが選ぶ | SQL 対象外は Data Agent へ。実行開始後の失敗で経路を切り替えない |

どの構成も Catalog から業務定義を明示的に取得し、同じ集計 View を使います。SQL 経路は #1 の標準完成定義と本文が一致する場合だけ使います。定義の本文を変更した場合、SQL 固定構成は対応外、振り分け構成は Data Agent となります。SQL が任意の業務定義に追随したとは扱いません。

SQL の対応範囲は、設定済みの当月・前月について、純売上・粗利益・返金額・売上原価の月次合計、純売上または販売数量の商品別トップです。日本語・英語の明示した質問形式に限定します。自由な言い換え、条件の追加、カテゴリの月次比較、将来保証は SQL 対象外です。商品別トップが同額なら商品 ID の昇順で 1 件を返します。質問形式の例は公開問題 Q01・Q02・Q03・Q05・Q06・Q07 を参照できますが、実行側は問題 ID・正解・評価分類を読みません。

## 標準定義に戻して比較する場合

経路の判断理由が `UNSUPPORTED_DEFINITION` なら、業務定義の本文が SQL テンプレートの前提と異なるという意味です。SQL 固定では対応外、振り分けでは Data Agent に進みます。振り分けの故障ではありません。

定義を変えていた方は、次の順で標準定義に戻します。SQL 経路は本文全体の一致で判定するため、2 か所だけでなく**概要の全文**を戻します。

1. Knowledge Catalog で現在の `business-rules` Entry を開き、`overview` の内容を手元のメモへ控えます。過去の回答・台帳・退避ファイルは消しません。
2. Cloud Shell Editor で教材フォルダの `semantics/lab1-starter.txt` を開き、全文を `overview` に貼り付けます。続けて [#1 の手順 2](lab1.md#手順-2knowledge-catalog-で会社の業務定義を編集する7-分) の表どおりに 2 か所を置き換え、保存します。
3. #1 の手順 3 の `apply-rules` を実行し、Catalog から取得した標準定義を②③とローカルの控えへ反映します。
4. Checkpoint 診断を確認し、**新しい評価計画**を作ります。変更前の計画を使い回しません。定義変更後はバックアップも取り直します。

比較後に自分の定義へ戻す場合も、現在のファイルを退避してから保存済みの内容を戻し、同じ同期手順を使います。

## 実習

1. #2 完成状態を [Checkpoint](checkpoint.md) で確認します。評価の間は定義・設定・コードを変えません。
2. 次のコマンドで、3 問×3 構成の 9 試行を計画します。この段階では推論しません。

```sh
uv run --locked python3 -m workshop.benchmark plan --cases Q01 Q04 Q08 --repeats 1 --cache on --route data_agent --route verified_sql --route router
```

3. 表示された計画 ID を使って実行・費用照合します。料金方式を確認できた場合だけ `on-demand` を指定します。

```sh
uv run --locked python3 -m workshop.benchmark run --batch BATCH_ID
```

全試行の終了後に費用を照合します。

```sh
uv run --locked python3 -m workshop.benchmark collect --batch BATCH_ID --billing-mode on-demand
```

4. Web 画面の URL の末尾に `/benchmarks` を付けて開き、計画を選びます。構造化回答の検査、質問分類ごとの対応範囲、選択経路と実際の処理、費用の内訳を比べます。反復する場合は `--repeats 2` で別の計画を作ります。小規模な結果を公開 8 問全体や本番の成績として扱いません。

単発で試す場合も、設定ファイルを書き換えずに指定できます。

```sh
uv run --locked python3 -m workshop.root_agent --route router --cache on --question '2026年8月の純売上はいくらですか。'
```

## 見るポイント

- SQL 固定構成が対応外の質問を返したら、実装のクラッシュとは別に `unsupported` として集計します。回答すべき質問で答えなかった場合は成功ではありません。将来の質問でも、単なる対応外と根拠に基づく適切な判断保留は区別します。
- 期待経路との一致は振り分け構成だけに表示します。記録は固定構成でも保持し、回答の合否には使いません。
- SQL 経路の実行前にジョブ ID とパラメータを保存し、`jobs.get` の結果で ID・Project・配置・SQL・パラメータ・時刻を照合します。キャッシュヒットで参照テーブルが空なら、取得元は未確認のままです。現時点の過去ジョブ補完は Data Agent 経路が対象で、SQL 経路へ証拠を流用しません。
- Data Agent を呼ばなかった完了実行は、Data Agent 分を「呼び出しなし・0」と表示できます。Root モデルや SQL の費用が消えるわけではありません。失敗・中断で未報告の使用量がある場合は未算出とします。
- 取得元の確認と回答の正しさは別です。ジョブ ID の直接対応でも、SQL の意味・期間・回答文まで正しいことを証明しません。
- SQL 経路の新しい管理対象リソースはありません。問い合わせの一時結果は BigQuery の通常の仕組みを使い、永続テーブル・Agent・バケットを追加しません。片付けは既存の teardown です。ジョブ履歴・観測記録の即時削除は行いません。

## 振り返り

「今回の質問のうち、どれを定型集計として管理するか」「対応外の質問をどう扱うか」「品質条件を満たしたうえで費用を抑えられるか」を判断します。SQL 経路が安くても、答えられる質問が減っていれば、それを含めて評価します。今回の比較は、自分の用途に合う採用条件を考えるためのものです。

## 処理時間と SQL 照合の読み方

全試行の中央値には対応外で短く終了した試行も含みます。追加の「共通回答試行の中央値」は、全構成が回答できた同じ質問・同じ回だけの時間です。回答した誤答は含め、適切な判断保留も対象とします。対象の問題と回、対象外の理由を画面で確認し、全体の速さや品質の順位と混同しないでください。全試行終了前は未算出です。

SQL の大小文字差は自動で全て同一視しません。単純な SELECT の `AS` 直後の列別名と、その別名だけを項目にした `GROUP BY`・`ORDER BY` の参照を補正できる場合は、取得元を `matched_alias_estimate` とし、費用詳細の `sql_matching` に差分を残します。たとえば `AS MONTH … GROUP BY MONTH` と `AS month … GROUP BY month` の差は対象ですが、`WHERE`・`HAVING`、`t.month` のような修飾付きの名前、式や関数の中の差は未一致のままです。未算出をなくすために、テーブル名・関数名・文字列まで小文字にしないでください。
